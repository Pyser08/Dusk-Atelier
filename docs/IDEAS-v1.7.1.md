# v1.7.1 장기기억 프로젝트 — 사용한 아이디어와 측정 결과

> 브랜치 `feat/1.7.1-longterm-memory` · 설계 원문 `v1.7.1-longterm-memory-plan.md`
> 측정은 **모델 없이 만든 가상 시나리오(추정치)** 입니다. 실측 절차는 `docs/MEASURE-v1.7.1.md`.

## 1. 한 줄 요약
기억을 "무엇을 했나"만 쌓던 구조에서, **얼마나 확실한가 · 지금도 참인가 · 누가 아는가 · 어떻게 느끼는가 · 서로 뭘 기대했나**까지 구분해 쌓고, 그중 필요한 것만 요청에 넣는다. 사용자는 **들어가는 로어를 직접 고칠 수 있다.**

## 2. 핵심 아이디어

### 1단계 — 신뢰도와 충돌 처리 (`memorytrust.js`)
- **사실/추정 구분 `kd`(f/i)**, 사실 확실성 `fc`(H/M/L), 해석 타당성 `ic`. 추정은 주입 시 `[inferred, uncertain]` 꼬리표가 붙고, 추정이 사실을 덮어쓰지 못한다.
- **속성 `attr {c,k,v,cond,tm}`**: 취향·관계·직업처럼 "지속되는 상태"를 키로 관리. 같은 키의 새 값이 오면 옛 값은 `was: …`로 이력 처리.
- **충돌 분류**: 조건부 / 과거 / 변화(나중 메시지) / 모순 후보. 확신도 비교, 동률·불명이면 **보류(hold)**. 낮은 확신의 추정은 확정 기록을 끝낼 수 없다.
- 같은 사건이 여러 번 나오면 출처만 늘리고(중복 제거) 횟수 `m`을 올린다.
- **필드 단위 잠금(lock)**: 사용자가 고친 필드는 자동 분석이 덮어쓰지 않는다. 한 단계 **되돌리기(undo)**.

### 2단계 — 감정 게이지와 검색키 (`memoryemo.js`, `memorykeys.js`)
- 감정을 한 단어가 아니라 **게이지 0–10 정수**(신뢰·호감·적대·의존·존경·공포)로 공존시킨다. 모델은 **±1~3 변화량과 근거(why)**만 내고, 합성 꼬리표는 코드가 만든다(충돌하면 `[conflicted]`).
- 값이 없으면 "미설정", 0은 "없음". 새 관계의 초기값은 비워 둔다.
- 위키 `affinity.score`는 호감 꼬리표로만, 대상 `{{user}}`, 쌍당 1회 이관(해제 가능).
- **검색키 `keys`(최대 3)**: 나중 장면에서 언급될 구체어(물건·장소·주제)를 저장 → 현재 장면에 그 단어가 나오면 **등급이 낮은 기록도 끌어올린다**. `evalRetrieval`로 포착률/배제율을 잰다.

### 3단계 — 관점·속마음·기대 어긋남 (`memoryinner.js`)
- `pov`: 같은 사건을 다르게 받아들이는 두 인물의 관점. `self`: 속마음(feel)과 추정 원인(cause, `ic` 필수). `exp`: 서로의 기대와 말하지 않은 어긋남.
- **중요한 응답(장면 전환 또는 등급 B+)에서만** 받는다 → 토큰 낭비 방지. 주입은 `inject.stage3` 스위치로 끌 수 있다.
- 긴장이 쌓이면 `hints`로 다음 분석에 힌트를 준다.

### 4단계 — 토큰을 아끼는 장치
- 분석 시스템 프롬프트를 압축·병합해 증가분을 **+716 → +428 토큰/호출**로 줄였다.
- 새 필드는 전부 **선택(optional)**. 1.7.0 기억은 마이그레이션 없이 그대로 동작하고, 다시 나온 기록만 새 필드를 채운다(`check-migration.mjs`로 검증).
- 무효 처리된 기록·잠긴 필드는 주입에서 제외, 섹션이 비면 제목도 뺀다.

### 5단계 — 사용자 편집 (이번 수정의 핵심)
- **주입 로어 편집기**(고급 화면 모드, "기억 방식" 박스 바로 아래): 실제로 들어가는 `[Dusk Memory]` 블록을 섹션별로 보여주고 **줄 수정 / 숨김 / 원래대로**, **내 로어 추가·수정·켜고 끄기·삭제**, 총 토큰 표시, 복사.
- 저장 방식: `folder.lore = {edit:{줄해시:{from,text}}, hide:{…}, add:[…]}`. 수정은 **요청에 넣는 순간에만 적용**되고 저장된 기억은 건드리지 않는다.
- 줄은 분석마다 다시 생성되므로 수정은 **원문 줄의 해시**에 묶인다. 원문이 바뀌면 조용히 사라지지 않고 **"적용 안 됨"**으로 내려와 "내 로어로 옮기기/지우기"를 고르게 한다. 오래 가져갈 내용은 "내 로어"가 정답.
- 기억이 없어도 내 로어는 주입된다(notes-only).
- 별도로 저장된 기록·감정·기대 자체를 고치는 **"기억 데이터 편집 (상세)"**도 유지(아래쪽).
- Risu 로어북을 새로 만들지 않는다. `beforeRequest` 훅 주입이 기본, 훅이 없을 때만 `da_mem` localLore 한 항목으로 대체.

## 3. 측정 결과 (가상 시나리오, `tools/sim-measure.mjs`)
60턴, 4명, 의미 있는 사건 7개(취향 변경·비밀·추정·약속·검색키 등)를 **같은 사건을 1.7.0 방식(새 필드 없음) vs 1.7.1 방식**으로 기록했다고 가정.

| 항목 | 1.7.0 | 1.7.1 |
|---|---|---|
| 분석 호출 시스템 프롬프트 | 632 토큰 | 1060 토큰 (**+428/호출**) |
| 주입 블록 (16건, 일반 장면) | 336 토큰 | 358 토큰 (**+22, +7%**) |
| 3단계 끔 vs 전체 | – | 이 시나리오에선 동일(중요 사건에 관점·기대가 안 걸림) |
| 프로브 5개 중 필요한 기억 포착 | 5/5 | 5/5 |
| 추정을 추정으로 표시 | 사실처럼 표시 | `[inferred, uncertain]` 표시 |
| 취향 최신값 (커피→차) | 둘 다 섞여 나옴 | 인물 요약은 "차 (was: 커피)", 단 "Story so far"에 옛 줄이 남음 |
| 비밀 범위 | 없음 | "Knowledge limits"로 아는 사람 표시 |

**읽는 법**
- **토큰**: 비용은 대부분 *분석 호출*(+428/호출)에서 나고, *요청마다 들어가는 블록*은 +7% 정도로 작다. 호출 수가 많으면 분석 비용이 지배적이다.
- **정확도**: 검색 포착은 이 작은 시나리오에선 천장(5/5)이라 차이가 안 보인다. 검색키의 이득은 기록이 수백 건이고 낮은 등급 기록이 필요한 장면에서 나타난다(→ 실데이터로 `measure-memory.mjs --cases`).
- **이어쓰기(연속성)**: 숫자로 직접 못 잰다. 대용 지표로 "추정 표시·비밀 범위·옛값 처리"만 확인했고, 실제 어긋남 여부는 `MEASURE-v1.7.1.md` ④의 직접 점검이 필요하다.

## 4. 측정에서 드러난 한계 (다음 작업 후보)
1. **옛 값이 "Story so far"에 남는다**: 속성이 바뀌어도 장면 요약 줄 "커피를 즐겨 마신다고 말함"이 그대로 나와 최신값과 섞인다. → 속성이 대체된 기록의 장면 줄을 숨기거나 `(옛)` 표시.
2. **새 관계에 음수 변화를 주면 게이지가 0으로 막힘**: 초기값이 "미설정"인데 −2가 오면 `trust 0`으로만 보인다. 부정 방향 정보(−2 사유)가 사라진다. → 첫 변화가 음수일 때 기준값(예: 5)에서 시작할지 결정 필요.
3. 낮은 등급(D) 일상 기록이 "Key moments"를 채운다 → 예산이 남을 때만 넣는 상한 검토.
4. 주입 로어 수정 중 **화면(e2e) 점검은 아직 안 함** — 직접 열어 확인 필요.

## 5. 사용자가 직접 할 검증
1. 고급 모드 → 기억 탭 → "기억 방식" 아래 **주입 로어 편집**을 열어 줄 수정/숨김 → 다음 요청의 실제 프롬프트에서 반영되는지.
2. 기억이 새로 분석된 뒤 수정이 "적용 안 됨"으로 내려가는지, "내 로어로 옮기기"가 되는지.
3. 실제 채팅의 기억 JSON으로 `node tools/measure-memory.mjs 기억.json --cases cases.json`.
